# AGENTS.md — BrandLoop

Everything an agent (or a new developer) needs before touching this repository.
Read this first; it records decisions that are **not** obvious from the code.

---

## 1. What this is

BrandLoop is a personal-branding automation tool. A user signs up, states a niche
and their own opinions, and gets a content plan. The system writes posts for X
and LinkedIn, DMs each draft to the user on Discord for approval, and hands back
a pre-filled composer link so publishing is one click.

**The product decision that shapes everything:** BrandLoop does not publish on
the user's behalf. It assists. Every post is approved by a human in Discord
before anything goes out. That is a PRD requirement (§2), not a shortcut — it is
why there is no stored X or LinkedIn credential anywhere in this codebase.

**Two processes, two ports:**

| Process | Port | Start |
|---|---|---|
| Express API (`src/`) | 8080 | `npm start` (root) |
| Next.js dashboard (`dashboard/`) | 3000 | `npm run dev` (dashboard/) |

Both must be running for the dashboard to work.

## 3. Status

### Done

**Phase 1 — the whole loop, working end to end.**

- Auth: register, login, JWT in an httpOnly cookie, bcrypt hashing.
- Google sign-in, optional and off unless `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`
  and `GOOGLE_REDIRECT_URI` are all set. The API does the code exchange, so the
  client secret never reaches the dashboard; the dashboard holds the public client
  ID and derives the redirect URI from its own address. Accounts are matched by
  verified email, so a password account and a Google sign-in with the same address
  are one account, and an unverified one is verified by the act of signing in.
  A `state` cookie is checked on the way back — without it, a callback URL carrying
  someone else's code would sign the victim in as the attacker.
- Content plans: generation, 7/30-day windows, per-slot themes, a planned/news mix.
- News sourcing from Google News RSS — real URLs only, so citation hallucination
  is structurally impossible. Personalisation happens at *selection*, not in the
  query (see gotcha 6.4).
- Post generation for X and LinkedIn, with hard per-platform character limits.
- Discord: `/connect`, `/status`, `/plan`; drafts DM'd with Approve / Reject /
  Edit; edits re-render the message in place.
- Assisted publishing: X gets a genuinely pre-filled composer link; LinkedIn
  cannot, so it gets a copy-and-open page (see §5).
- Daily scheduler advancing one slot per day at 09:00.
- Quotas on every paid call, consumed **before** the request.

**The Next.js dashboard** — added after Phase 1 at the user's request.

- Sign-up / login / logout, profile editing, quota display.
- Workspace: plan rail, per-slot Generate, drafts, workflow explanation.
- Slot editing (angle + planned/news) before generation.
- Draft editing from the dashboard, sharing one service with the Discord modal.
- Discord linking with polling.
- `/billing` — the plans page (Free / Creator / Pro), and `/billing/pay` — the
  local checkout. **There is still no card path and no payment provider**, and
  that is now a deliberate choice rather than a deferral: a Pakistani gateway
  means a merchant account (company registration, NTN, a signed contract), which
  is a business process, not a commit. So the customer pays by bank transfer,
  Raast, JazzCash or Easypaisa, states the transaction reference, and **the plan
  activates on submit** — `PAYMENT_AUTO_VERIFY` defaults on, because a customer
  who has paid and is told to wait for a human is a customer who has left. The
  operator then reconciles the claim against their own statement and confirms or
  revokes it (one tap in a Discord DM, or from `/admin/payments`). A revoke
  restores the account's previous plan and expiry, which is why the grant records
  what it replaced — see gotcha 6.14. A tier is real anyway: every signup gets 30
  days of Pro, a coupon can grant Pro or unlimited usage, and the price, term and
  limits on the cards are all read from `/api/billing` rather than kept as
  literals here, so a card cannot advertise a ceiling or a price the API does not
  enforce.
- `/feedback` and `/admin/coupons`, `/admin/feedback`, `/admin/payments` — the
  feedback form and the three admin pages. The admin pages are guarded three deep:
  `proxy.ts` wants a cookie, the page calls `notFound()` for a non-admin, and the
  API returns 403 regardless. `/api/admin/*` is the only router with
  `requireAdmin` on the router itself.
- Brand: `public/BrandLoop-logo.png`. The file is RGB with **no alpha channel**
  and has the wordmark inside it, so it is drawn as a rounded tile
  (`components/brand-logo.tsx`) beside a real text label. Do not drop the raw
  file onto a dark surface, and do not rely on it to name the product at UI
  sizes. The artwork's own palette is **blue and teal** on white, which does not
  match the app's warm amber tokens — measured from the file, not assumed. That
  is why the logo never sets a colour anywhere: it stays inside its tile and the
  interface keeps its own palette. Do not "fix" the mismatch by recolouring the
  logo, and do not pull its blue into the design system.
- The desktop theme switch lives in the sidebar's **top row**, beside the brand.
  It is shared with the mobile top bar, where it already was.
- `/compose/[postId]` — the LinkedIn copy-and-open page. Copies the **image** as
  well as the text (as PNG — Chromium refuses `image/jpeg` on the clipboard),
  with a Download fallback. The bytes come from the dashboard's own route
  `GET /api/posts/[postId]/image`, because the browser cannot *read* the API's
  `/media` URL — no CORS, and a canvas drawn from it is tainted.

**Local payments** — added after the dashboard, when the owner asked for a way to
actually take money in Pakistan.

- `src/models/Payment.js` is one claim: who paid, what it bought, the reference
  the customer typed, and the single decision on it. Every transition is one
  `findOneAndUpdate` with its precondition **in the query**, because two admins,
  or one admin in Discord and the dashboard, will act on the same row at once.
- `src/services/grantService.js` was extracted so a purchase and a coupon cannot
  drift: `computeCouponGrant` moved there untouched, `computeTierGrant` and
  `restorePreviousGrant` joined it, and `couponService` re-exports the old name so
  nothing that used it changed.
- Grants **extend, never replace**: a renewal adds to the end of the period, and
  so does an upgrade — the days already paid for are not thrown away. A
  **downgrade is refused** (`purchasability`), because the account holds one plan
  with one expiry and selling a cheaper tier would silently delete paid-for time.
- The instant path is bounded on purpose: one unreconciled claim per user, a
  price ceiling (`PAYMENT_AUTO_VERIFY_MAX_PKR`), and a one-tap revoke. Set
  `PAYMENT_AUTO_VERIFY=false` to put a human in front of every purchase instead.
- `paymentQueue.js` DMs every admin and is the only button handler in
  `interactions.js` with a role check — see gotcha 6.13.
- Notification is best-effort and never fails a purchase; a claim with no admin to
  DM is logged and waits on `/admin/payments`.

**Hardening done since Phase 1** (each was a real bug found by running it):

- `generateSlot` retries only the platform that failed, instead of marking the
  slot complete on a partial success and never retrying.
- Slot failures persist as `lastSkipReason` so they survive the toast.
- A post longer than Discord's 2000-char message limit no longer blocks delivery.
- The dialog primitive can scroll, so tall dialogs are usable.
- Profile saves work at all — the PATCH schema required every field.
- The link-code route actually applies `requireAuth`.
- X threads: the model can write a multi-part thread, delivered as separate
  copy blocks with the composer link carrying part 1 only.
- Console errors from Base UI `Button render={<a/>}` are gone.
- Route failures are handled in-app rather than by Next's error page:
  `(workspace)/error.tsx` covers a page, and `app/error.tsx` covers the shell
  itself — a layout error escapes the boundary in its own segment. Both render
  the same screen (`components/route-error.tsx`), which names the cause: API not
  running, database unreachable, or unknown.
- The theme stopped being a `<script>` element: it is a cookie the server renders
  and `light-dark()` resolves in CSS, so React never client-renders a script
  (gotcha 6.9).
- A database lost at runtime answers 503 with `Retry-After` instead of a generic
  500, and fails immediately rather than buffering for ten seconds (gotcha 6.10).
- 150 tests, `tsc` and eslint clean.

**Phase 3 — image generation.** Built on OpenAI, where the quota exists; the
original deferral (A3) was about the **Gemini** key, which still has none.

- `services/ai/imageGenerator.js` writes one JPEG per eligible post to
  `media/{postId}.jpg`, served at `/media/…`. The prompt is the model's own art
  direction + the user's niche + `IMAGE_STYLE_SUFFIX` (palette, and no lettering
  — the live render contained no legible text).
- Wired into `generateSlot` **after** the text is persisted and **before** the
  DM, and into `regeneratePost` for the same reason: rejecting the writing is
  not a decision about the artwork.
- Any failure — weekly cap, moderation, timeout, provider error — leaves the
  post queued text-only with the reason stored on `Post.imageSkipReason` and
  shown in the embed. **An image failure never blocks approval**, and there is
  no retry: one image is the most expensive call in the pipeline (~$0.04, ~17s).
- `generateImage()` now exists on **both** providers. OpenAI's is verified live;
  Gemini's is written but unexercised, because that key still has zero image
  quota (it degrades to text-only rather than losing the post).
- `npm run probe -- --images` exercises the real generation path — opt-in,
  because the call is paid.
- Full spec: `docs/IMPLEMENTATION-PLAN.md` §7, with the build's deviations in
  §0.6.

**Deployment.** `Dockerfile` builds the API (Express + the Discord gateway +
the scheduler, one process), `dashboard/Dockerfile` builds the dashboard as a
Next.js standalone server, and `docker-compose.yml` runs both with a volume for
`media/`. Both containers run as the non-root `node` user and define
healthchecks; verified end to end at 85 MB and 48 MB resident. Docker is an
*option* beside the PRD's PM2 + Nginx plan, not a replacement — and
`docs/DEPLOYMENT.md` records why a host that suspends idle containers cannot run
this one at all: the gateway drops and the cron job dies with no error. A push to
`main` publishes both images to GHCR
(`.github/workflows/publish-images.yml`), so a machine that only runs the app can
`docker compose pull` instead of building it.

### Remaining

Nothing in the planned scope. What follows is deliberately unbuilt, not pending.

**Explicitly out of scope — do not build:**

- Phase 2: LinkedIn Community Management API. (Would replace the LinkedIn
  publisher branch and nothing above it — that seam is deliberate.)
- Phase 4: short video / Veo.
- Stripe, BullMQ/Redis, browser automation. Note that local payments are **in** —
  what is out is a *processor*. The seam for one is already here: a `Payment` row
  carries `source` and `providerRef`, and `reviewPayment` is the only thing that
  writes a tier, so a webhook would call exactly that path and skip the human.
  Browser automation in particular is forbidden: driving a real session to post on
  the user's behalf breaches LinkedIn's terms and risks **the user's** account.

## 4. Coding standard — comments (an explicit requirement)

This is a graded requirement from the PRD, not a style preference. **Every module
and every non-trivial function carries a comment explaining WHY, not WHAT.**

- File headers state RESPONSIBILITY, the reasoning behind the design, and
  `DOES NOT OWN:` so ownership is explicit.
- Comments explain the decision and what it costs. `// increment counter` is
  noise; "consumed BEFORE the call, so a failure never still bills" is the point.
- Where a comment and the code disagree, **the comment is usually describing the
  intent and the code is the bug.** Two of the worst defects in this repo were
  exactly that: `userRoutes` documented "everything is optional" while the schema
  required every field, and the link-code route documented `requireAuth` while
  never applying it. Read the comments, then check the code honours them.

## 5. Architecture decisions worth knowing

**Next.js is a backend-for-frontend, not a browser client.**

```
Browser ──same-origin──▶ Next.js server ──server-to-server──▶ Express API
```

`dashboard/lib/api.ts` is the *only* thing that calls the Express API, and it is
`server-only`. This was forced by a finding: the API has **no CORS middleware**,
so a browser call would be blocked before it left. Proxying was chosen over
adding CORS. Three things fall out: no CORS config, the JWT lives in an httpOnly
cookie no script can read, and the API needed no changes to serve a browser app.

**One service per operation, two thin entry points.** Approval and rejection go
through Discord only. Editing is reachable from Discord *and* the dashboard, so
it delegates to a single `updatePostContent` rather than duplicating guards —
`postRoutes.js` explains why two code paths would eventually disagree about what
a post is allowed to become.

**Platform capabilities differ, and the code says so rather than pretending.**

- X pre-fills its composer from a URL parameter. Its link goes straight there.
- LinkedIn cannot. Its share endpoint builds the card from the destination page's
  Open Graph tags; there is no parameter that seeds the post body. So its link
  routes through `/compose/[postId]`, which puts the text on the clipboard and
  then opens LinkedIn. `linkedinPublisher.js` reports `prefilled: false`
  truthfully rather than promising something that will not happen.
- The **image** has no URL route into either composer, so for LinkedIn it travels
  the same way the text does: the compose page copies it to the clipboard as PNG
  and the user pastes it. There is no other honest option — attaching media needs
  the Community Management API (Phase 2, out of scope), and browser automation to
  fake a session risks the user's own account.

## 6. Gotchas that have already caused bugs

**6.1 Zod requires every key unless marked `.optional()`.** A PATCH schema
without `.optional()` rejects every field the client did not send — and the error
names fields the user never touched, so it reads as nonsense. This broke every
profile save. Applies to any new PATCH body.

**6.2 Discord caps message content at 2000 characters and rejects the *whole*
message with `50035` if any part exceeds it.** X fits at 280; a LinkedIn post
reaches 3000, so **every** long LinkedIn DM silently failed to send. Long posts
now move into the embed description (4096 limit). Any new Discord payload needs
this check.

**6.3 `requireAuth` is applied per-router, except in `authRoutes.js`** — that
router also serves public routes, so it goes on the individual route. A guard
that reads `req.user` cannot detect the middleware's absence; it just fails
closed, which looks like working authentication.

**6.4 `buildQuery` uses the niche only.** Appending the user's `inputPoints`
(full sentences) to the RSS query returns **zero** candidates; the niche alone
returns 25. Personalisation moved to the selection step.

**6.5 All quotas are consumed BEFORE the paid call.** A crash between the call and
the increment hands out free work, and a run of those is how a quota stops
controlling cost.

**6.6 Do not trust a vision model's UI review.** It reported a contrast failure
and wrong fonts on this dashboard; axe-core found 0 violations and the computed
font was correct. Run `axe-core` — measure, do not eyeball.

**6.7 Discord drops a message's attachments on edit unless they are re-sent.**
Re-rendering an image-bearing DM without the file left the message with **no**
attachment at all — the image vanished from a draft nobody had touched. The
payload now re-attaches the file on every render, and a regression test pins it.
The tempting "don't re-upload what is already there" optimisation is the bug.

**6.8 A parameter the callee does not destructure is silently dropped.**
`logGeneration` computed `estimatedCostUsd` and passed it to
`GenerationLog.record`, which never picked it up — so every row stored `null`
and the PRD §7 cost table summed to `$0`, making the quotas look free. Nothing
errored; the number was simply absent. Watch for this whenever a wrapper
forwards an options object.

**6.9 React 19 forbids a `<script>` in the render tree, and the rule is about
rendering, not about who wrote it.**
It removed `next-themes` first: that library applies a theme from inside a Client
Component, so every client re-render of its subtree logged "Encountered a script
tag while rendering React component". The hand-written replacement kept a script
in the root layout and hit the same rule anyway — **any** client-side re-render of
the root tree logs it, and an error recovery does exactly that, so one API
failure was enough to put the warning on screen. `next/script` did not help
either; Next still renders the element.

The theme is now cookie-driven and script-free: the root layout reads the cookie
and renders `data-theme` into the HTML, `globals.css` resolves the palette
through `light-dark()` against `color-scheme`, and `system` is the *absence* of
the attribute, left to the media query. Correct in the first byte, with or
without JavaScript. Before adding any script to a component, check that a
callback, a CSS rule, or a server render cannot do the job instead.

**6.10 A database outage is a 503, not a 500 — and the API fails fast for it.**
Every authenticated route needs Mongo (`requireAuth` re-reads the user), so a
connection lost at runtime used to surface as a generic 500 on perfectly valid
requests. `errorHandler` now checks `isDatabaseConnected()` and answers 503 with
`Retry-After`, while `ApiError`s keep their own statuses — an expired session
must stay a 401 even during an outage, or the dashboard would show an outage
instead of asking for a sign-in. `bufferCommands: false` in `db/connect.js` is
part of the fix: without it the query waits out the driver's buffer timeout
first, turning a blip into a ten-second hang.

**6.11 `client.guilds.fetch()` returns `OAuth2Guild` objects, which have no
`commands` manager.** Registering slash commands by iterating that result threw
"Cannot read properties of undefined (reading 'set')" for every guild, and the
per-guild `catch` in `registerCommandsInGuild` swallowed it — so the run still
logged "global + 1 guild(s)" while no guild had a single command. The only trace
was a warning that reads like a permissions problem, and the failure mode is
quiet: the commands still work once global registration propagates, so it looks
like nothing is wrong. Iterate `client.guilds.cache` instead; it holds real
`Guild` objects and is complete by `clientReady`. Any other place that reaches
for the API to enumerate guilds has the same trap.

**6.12 Nothing in the test suite imported a router, so a broken import in the
auth path passed all 230 tests — and would have stopped the API from booting.**
A new service under `src/services/auth/` imported `../utils/ApiError.js`, which
resolves to `src/services/utils/` and does not exist. Module resolution happens
at import time, so the failure had no earlier symptom than the process that
imports it — and the API imports every router at startup. It was caught by a
hand-typed `node -e "import('./src/routes/authRoutes.js')"`, which is now
`tests/module-loads.test.js`: it imports every file in `src/routes/` and
`src/services/`. Loading a module does not prove it works; it proves it exists,
which is the class of mistake `tsc` cannot see in plain JavaScript and a suite
that never touches the entry points misses entirely. Any new directory of
modules deserves the same two lines. It now walks `src/models/` too, because a
model whose consumers do not exist yet is exactly where that gap is widest.

**6.13 A DM fanned out to several people is not access control.** The draft
buttons rely on isolation: the approval message goes to one person's DM, so being
able to press Approve *is* the authorisation, and those handlers never compare
`interaction.user.id`. Copying that pattern for the payment notice — which is
sent to **every** admin — would have let any of them grant a plan, and would have
kept letting them after a demotion. `handlePaymentDecision` therefore re-reads the
actor from the database and requires the admin role, the same way `requireAdmin`
does for HTTP. Before fanning any message out to more than one person, add the
check that the single-recipient case made unnecessary.

**6.14 Granting access before the money is confirmed is only safe if the grant
records what it replaced.** `PAYMENT_AUTO_VERIFY` activates a plan on submit, which
puts a customer's access ahead of the operator's attention — the thing that makes
local manual payment tolerable. It is only reversible because
`previousPlan`/`previousPlanExpiresAt` are snapshotted **before** the plan is
moved, so a revoke restores exactly what the account had rather than dropping a
paying customer to Free. Two rules follow, and both are tested: the snapshot is
written in the same update as the grant, and `restorePreviousGrant` **refuses** to
use it once the account's expiry no longer matches what that grant wrote (a newer
purchase has landed, and restoring the old value would silently delete days the
user paid for). Any future "activate now, verify later" flow needs both halves.

## 7. Running it

```bash
# root — API on 8080
npm start            # or: npm run dev (nodemon)
npm test             # node --test, 298 tests
npm run probe        # validates the AI models and every credential
                     # `npm run probe -- --images` also generates one for real
npm run seed         # demo account: demo@brandloop.local / demo-password-123

# dashboard — on 3000
cd dashboard && npm run dev
npx tsc --noEmit     # must be 0 errors
npx eslint .         # must be 0 errors
```

**Docker** — both processes without two terminals (detail in
`docs/DEPLOYMENT.md`):

```bash
docker compose up -d --build   # API on 8080, dashboard on 3000, media on a volume
docker compose ps              # both must report healthy
docker compose down            # keeps the media volume; `down -v` deletes it
```

The dashboard image bakes `NEXT_PUBLIC_DISCORD_INSTALL_URL` in at **build** time
(Next inlines `NEXT_PUBLIC_*`), which is why compose reads it from `.env` and why
changing it needs `docker compose build dashboard`. The API's build stage uses
the full `node:22-bookworm` image rather than `-slim` on purpose: it carries the
compiler bcrypt may need, so no build ever reaches for a Debian mirror.

**Before calling anything done:** `npm test`, `tsc --noEmit`, `eslint .`, and a
console sweep of `/workspace`, `/drafts`, `/settings`, `/billing` and
`/billing/pay` — all currently clean, and regressions there are the thing most
likely to slip through.

**Payments are off until an account is configured.** `PAYMENTS_ENABLED` is
*derived*: with no `PAYMENT_BANK_ACCOUNT_NUMBER`, `PAYMENT_JAZZCASH_NUMBER` or
`PAYMENT_EASYPAISA_NUMBER` in `.env`, there is no way to pay, the billing page
keeps its "not set up" state, and `POST /api/payments` answers 400 — a deployment
cannot offer a checkout it has nowhere to receive. `npm run seed` creates the demo
account but sets no payment details, so a local run of the purchase flow needs
those three lines filled in.

**Operational scripts** (they take `--email` deliberately, so fixture rows from
test runs can never be sent to a real account):

- `scripts/redeliver-posts.mjs --email …` — re-sends generated-but-undelivered posts.
- `scripts/refresh-approval-messages.mjs --email …` — re-renders existing DMs in
  place when a publisher's link target changes. Handles approved posts with the
  published layout, since re-rendering them as an approval prompt would put the
  buttons back and invite a second publish.

## 8. Working agreement — commit and push after every change

An explicit instruction from the owner, and it outranks tidiness: when work in
this repository is to be committed and pushed, **each change lands as its own
commit and is pushed immediately.** Do not gather a session's work into one large
commit at the end.

- **One logical change, one commit.** A feature, a bug fix, a doc correction and
  a UI tweak are four commits even when they happen in the same sitting.
- **Push as soon as it is committed.** Leaving commits local defeats the point:
  the images publish from `main`, and the owner may be reviewing from another
  machine.
- **Gates before the commit, not after.** `npm test`, then `npx tsc --noEmit` and
  `npx eslint .` in `dashboard/`. A failing gate means fixing it, then committing
  — never `--no-verify`, never a "fix it later" commit.
- **Never commit** `.env`, `media/`, build output, or state left behind by a
  fixture run. Check `git status` before staging.
- **The message says why.** Same standard as the comments in the code (§4): the
  reasoning and what it costs. Where a claim is measurable — a contrast ratio, a
  test count, a build size — the measurement goes in the message.
- **Work that may be reverted gets its own commit**, so it can be reverted alone
  without unpicking whatever came after it. The nav contrast change is the
  example: it was requested as a separate, revertable commit.

## 9. Environment and secrets

`.env` is gitignored and holds the Discord token, Mongo credentials and the AI
key. Never commit it, never log it.

`.env.example` is the template. **Keep it in sync** — it documents every
required and optional value, including `DASHBOARD_BASE_URL` (the LinkedIn
copy-and-open page), `IMAGE_MODEL` (Phase 3) and the `GOOGLE_*` trio (sign-in).
Two notes on the Google values: the client ID is public by design and so appears
in both `.env` files, while the secret is only in the root one; and the redirect
URI must match the console registration character for character, because a
mismatch surfaces as `redirect_uri_mismatch` on Google's own screen rather than
in any log of ours.

Model names live in env, never hardcoded in `src/` — the catalog moves fast and
`npm run probe` is the single place that validates them.

The payment block in `.env.example` is the same rule applied to money: the account
numbers, the PKR prices, the term and `PAYMENT_AUTO_VERIFY` all live there, because
each is the operator's decision rather than a property of the code. `README.md`
documents the flow for whoever is running it; nothing about it belongs in a
literal.

**Decided, worth knowing:** auto-verification of a transfer is impossible without
a processor, and a Pakistani processor means a merchant account. The honest
options were a human in front of every purchase — which loses the customer — or
granting on submit and reconciling after, which is what this does. A future
gateway webhook would write the same `Payment` row and call `reviewPayment`, and
the reconcile step would then be bookkeeping rather than a race with the
customer's patience.

## 10. Open questions

**The original LinkedIn delivery failure's root cause is known** (gotcha 6.2) and
fixed. What is *not* known is whether any LinkedIn post was lost before
`lastSkipReason` existed to record it. If a user reports a missing draft from
before this work, check for a `Post` with no `discordMessageId` and re-send it
with `redeliver-posts.mjs` rather than regenerating — the text already exists and
regenerating spends a model call.

**The free tier allows 20 requests per day, per model.** A 30-day plan at 3
posts/week needs ~27 writing calls, which exceeds one model's daily allowance. On
the free tier that plan cannot finish in a day. Rotating `TEXT_MODEL` between
models works because each has its own allowance; a paid key removes the problem.
This is a property of the tier, not of the code.
